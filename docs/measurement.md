# 測距の仕組みと、結果が合わないときの考え方

このツールは、スクリーンショットの点を地面上の位置に戻し、その間の距離を測ります。
画像上のピクセル数を、そのままゲーム内距離に置き換えるものではありません。
画像と編集内容は端末のブラウザ内で扱い、外部へ送信しません。

## まず押さえる3つの違い

| 項目 | 決めるもの | 間違ったときの影響 |
| --- | --- | --- |
| ゲーム描画領域 | 画像のどこからどこまでが元のゲーム映像か | 補正に使う高さ・中心がずれ、距離比まで変わる |
| カメラの校正 | 斜めから見た地面をどう平面に戻すか | 位置や方向によって距離の誤差が変わる |
| 距離スケール | 補正後の長さ1を、ゲーム内のいくつとして扱うか | 全距離が同じ倍率で変わる |

基準円にゲーム内半径を入力する操作は、最後の「距離スケール」を決めます。
ピッチ角や画角を自動で推定する操作ではありません。基準円の数値を変えても、
手前と奥の距離比の誤りは直りません。

## なぜ画像上の長さだけでは測れないのか

地面上では同じ長さでも、奥にあるものは画像上で小さく写ります。
また、地面の奥行き方向は、見下ろす角度によって縮んで見えます。
そのため、2点それぞれを地面上へ戻してから距離を計算します。

```text
画面でクリックした位置
  → 表示のズーム・スクロールを取り除いた、元画像内の位置
  → ゲーム描画領域とカメラ設定を使い、地面上の位置へ変換
  → 地面上の2点間の距離
  → 基準円のスケール、または最初の測距線に対する比率を適用
```

アプリの表示を拡大・縮小したり、スクロールしたりしても、同じ2点の測距結果は
変わらない設計です。グループ中心も、画像上ではなく地面上の位置の平均です。

### 絶対距離と相対距離

基準円に既知のゲーム内半径を設定した場合は、次の式を使います。

```text
スケール = 基準円のゲーム内半径 ÷ 基準円の地面上の半径
表示距離 = 地面上の2点間距離 × スケール
```

半径が未設定の場合は、最初の測距線を1とします。

```text
表示比率 = 測りたい線の地面上の長さ ÷ 最初の線の地面上の長さ
```

基準になる線を動かすと他の比率も変わります。削除すると次の線が基準になります。
基準線の長さが0、または端点のグループが空の場合は、有効な比率を計算できません。
「1.0000」と表示される基準線そのものは、補正が正しい証拠にはなりません。

## 投影パラメータの用語

UIと本文では「ピッチ角・垂直画角・ロール角」を使います。
「俯角」は下向きの角度を表す言葉として正確ですが、カメラの姿勢を調整するUIでは
「ピッチ角」に統一し、符号の約束を添えます。「縦画角」と「垂直画角」は同義で、
ここでは vertical field of view に対応する「垂直画角」を採用します。
「画面の傾き」は画像の回転や線路の方向とも読めるため、「ロール角」に置き換えます。

このツールのピッチ角は水平から下向きが正（0°より大きく90°以下）、90°で真下です。
ロール角は画像上の地面X軸・消失線が右下がりになる向きを正とします。
他のシステムの回転角を移す場合は、軸と符号の定義を確認してください。
内部名 `elevationDegrees` は既存の校正データとの対応を保つため維持します。

参考：[MathWorksのカメラ姿勢の定義](https://www.mathworks.com/help/driving/ref/monocamera.html)、
[OpenCVの主点・焦点距離の説明](https://docs.opencv.org/4.13.0/d4/d94/tutorial_camera_calibration.html)。

## 共通のカメラ設定は何を仮定しているか

初期値はピッチ角25.2°、ロール角0°、垂直画角9.92°です。
主点（投影の中心）の初期値はゲーム描画領域の中央です。
値の根拠と校正元の円弧への適合結果は、[校正記録](calibration/README.md)にあります。

| 設定・前提 | 意味 |
| --- | --- |
| ピッチ角 | 地面に対してカメラが下を向く角度。奥行き方向の縮み方に関係する |
| 垂直画角 | ゲーム映像の高さに含まれる視野の角度。ピッチ角などとともに遠近補正を決める |
| ロール角 | カメラの光軸回りの傾き。画面内の線路の向きとは別 |
| 主点 | 画像内の投影の中心。余白が非対称なら画像全体の中央とは一致しない |
| 平らな地面 | 測定点が同一平面上にある。坂・段差・空中の点は対象外 |
| 画像の縦横比 | 垂直画角を固定し、ゲーム側が横の可視範囲を変えると仮定する |

画素は正方形で、縦横を別々の倍率で引き伸ばしていないと仮定します。
全端末・全モードでカメラ設定が共通だと実証したわけではありません。
一つの画像で円弧がよく合うことと、別の画像でも測距が正しいことは別の検証です。

## 投影パラメータの手動調整

メニューの「高度な設定を表示」（初期状態OFF）をONにすると、基準パネルに
投影パラメータを表示します。画像を開いた後に入力し、「投影設定を適用」でまとめて反映します。
ピッチ角は0°より大きく90°以下、垂直画角は0°より大きく180°未満、ロール角は有限の度数です。
主点X・Yは検出された描画領域内の比率（0〜1）で、左上が (0, 0)、右下が (1, 1) です。
帯を含む画像全体に対する比率ではありません。

既存ピンと自由な円中心は、旧投影で画像座標に戻し、新投影で地面座標へ変換します。
画像上の位置は維持されますが、地面上の距離とグループ中心は再計算されます。
基準円は中心と変更前の地面X軸正方向の円周点を変換し、その距離から半径を決めます。
円周全体の形を保つ変換ではないため、適用後にゲーム内の円と合わせ直してください。
基準円のゲーム内半径と補助円の入力半径は維持します。補助円は新しい距離スケールで描画されます。

地面に投影できなくなる既存点や、カメラ前方に収まらなくなる基準円がある場合は、変更全体を拒否します。
適用1回がUndo／Redoの1操作です。表示とPNG出力は同じ設定を使います。
高度な設定をOFFにしても適用値は維持します。別の画像では、保存した基準があればそのカメラ設定、なければ初期値を使用します。
表示オプションは保存せず、ページを開き直すとOFFになります。

基準パネルで保存する基準は、円の地面座標・半径・ゲーム内半径と、その距離の意味を決めるカメラ設定の一組です。
画像寸法と帯の検出結果は持ち越さず、新画像の描画領域から投影を作り直します。
同じ撮影条件での解像度・外側の余白の違いには対応しますが、クロップやゲーム側のカメラ変更を補正するものではありません。
円の中心が新画像の描画領域外になるなど適用できない場合は、基準を部分適用せず初期設定で開きます。
「この画像の基準をリセット」は円の削除と初期カメラへの変更を一つの編集として扱い、ピンの画像座標を維持します。
保存レコードは変更せず、Undo／Redoで現在の画像の基準を戻せます。

## 帯があると、なぜ結果が変わることがあるのか

本来、同じゲーム映像に余白やプレーヤーの枠を足しても、距離比は変わってはいけません。
ただし、そのためには元のゲーム描画領域を正しく指定する必要があります。

現在の計算は、ゲーム領域の高さから焦点距離を決めます。

```text
f = ゲーム領域の高さ / (2 × tan(垂直画角 / 2))
cx = ゲーム領域の左端 + ゲーム領域の幅 × 主点X（初期値0.5）
cy = ゲーム領域の上端 + ゲーム領域の高さ × 主点Y（初期値0.5）
```

帯を含む画像全体の高さを使うと、fが過大になります。非対称な枠なら中心もずれます。
今回の例では奥側の縮みを戻す補正が不足し、奥の線が短く出ました。
誤差の大きさや向きは点の配置と中心のずれにも依存するため、
すべての画像に一律「7%足す」などの補正はできません。

### 自動除外の現在の限界

現在は画像を最大256 × 1024ピクセルにサンプリングし、外縁から単色または青い模様の
帯を探します。向かい合う帯がほぼ同じ厚さであることなどを条件に除外します。
条件を満たさない軸は、画像の端から端までを計算に使います。
これは「帯がないと確認できた」という意味ではありません。

通常の判定が失敗した場合、青い上下帯については各行の左右それぞれ外側25%を
追加で調べます。中央50%を避けるため、中央のホームインジケーターの影響を受けにくく
なります。青系の画素のRGB中央値から32を超えて離れた少数画素を除き、小さなカーソルの
影響を抑えます。残った画素がサンプル範囲の70%以上で、色のばらつきが小さいことを条件にします。
外側の細い枠は画像高さの4%まで探索し、上下でほぼ同じ厚さの帯が見つかった場合だけ
採用します。縮小で色が混ざった境界も、この厚さの条件で判定します。

これは画像に基づく判定であり、ゲームの帯挿入アルゴリズムを特定したものではありません。
左右まで広がる字幕、大きなプレーヤー操作部、非対称な帯、青い場面などでは、判定に
失敗・誤判定する可能性が残ります。基準パネル先頭の「ゲーム領域」で上下左右の除外幅を
整数pxで指定できます。破線で確認し、「適用」で反映します。自動検出した境界も確認してください。
帯を検出できた場合も、画像を開いた直後は領域の確認を案内します。正しければ「OK」で現在の領域を
確認済みにできます。「自動検出を適用」「画面全体を適用」、手動の「適用」も確認済みとして反映します。
領域を変更してもピンの画像位置は保ちますが、基準円の形と距離は再確認が必要です。
領域・状態・再投影した点はUndo／Redoで一緒に戻せます。領域は画像ごとに設定し、保存基準には含めません。

### 2026-09-26の比較で確認したこと

校正元とは別の5枚で、手前の線を1とした奥の線の比率を比較しました。
2本が実際に同じ長さであることを前提とした確認であり、ゲーム内部の座標を
取得して正解距離を確認したものではありません。

| 画像名 | 添付画像の表示値 | ゲーム領域を指定した概算 |
| --- | ---: | ---: |
| 画像1 | 1.0020 | 約1.00 |
| 画像2 | 0.9980 | 約1.00 |
| 画像3 | 1.0028 | 約1.00 |
| 画像4 | 0.9365 | 約1.00 |
| 画像5 | 0.9269 | 約1.00 |

改善前の自動判定では、添付された5枚のいずれも画像全体が描画領域になりました。
最後の2枚にはゲーム外の領域があるため、その判定は不適切です。
画像4では上下の帯の走査長が一致せず、画像5（プレーヤー枠付き）では外縁から帯を認識できませんでした。

再計算には、下表の表示サイズ上で目視した座標を使い、カメラ値は変更していません。
領域は `(左端, 上端, 幅, 高さ)`、点は `(x, y)` です。サイズは元ファイルの解像度ではありません。
元画像で再現する場合は、領域と全点を同じ座標系へ換算してください。

| 画像 | 計算用サイズ | ゲーム領域 | 手前の2点 | 奥の2点 |
| --- | --- | --- | --- | --- |
| 画像4 | 1877 × 1311 | (0, 198, 1877, 915) | (642, 978), (916, 912) | (150, 466), (384, 421) |
| 画像5 | 1200 × 886 | (11, 157, 1181, 555) | (421, 644), (594, 602) | (112, 325), (258, 296) |

`buildProjection` にこの領域を渡し、4点を `imageToGround` で戻して
「奥の長さ ÷ 手前の長さ」を計算すると、それぞれ約1.001、約0.997になりました。
点と境界が目視による概算なので、測距誤差が0.1%以内だという保証には使えません。
実際、同じ概算点で画像全体を使った値も、添付画像の表示値とは少し異なります。
この比較が示すのは、領域の修正だけで6〜7%程度の差をほぼ説明できることです。
画像はリポジトリに同梱していません。

### 青い帯の自動判定を改善した後の確認

校正元のスクリーンショットも含む添付6枚を、原寸・縦横1/2・縦横1/4で確認しました。
ChromiumとWebKitの計36ケースで、帯付きの2枚はゲーム領域を検出し、帯のない3枚と
プレーヤー枠付きの1枚は画像全体を維持しました。境界の許容差はサンプリング後の3pxです。
原寸での検出領域は、校正元スクリーンショット（1706 × 982）が約 `(0, 63, 1706, 829)`、
画像4（2388 × 1668）が丸め後 `(0, 251, 2388, 1166)` でした。
これは計算に使う領域であり、元画像やPNG出力から帯の画素を削除する処理ではありません。

ホームインジケーター、細い外枠、境界の色混合と、片側だけの帯・厚さの不一致・
過大な帯・大きな外枠を扱う回帰チェックを `tests/image.test.ts` に追加しています。

## 結果が合わないときの確認順序

1. **ゲーム描画領域を確認する。** 自動判定で合わない場合は基準パネルの「ゲーム領域」で
   帯・アプリ枠だけを除外します。ゲーム内HUDを含めた元の映像領域全体を使います。
2. **点の置き方を確認する。** キャラクターは頭や立ち絵の中心ではなく、地面への
   接地点を基準にします。床の同じ位置・同じ辺を選び、遮蔽や線の太さにも注意します。
3. **相対距離で確認する。** 実際に等しいと分かる長さを手前・奥、異なる方向で
   比較します。一方向の一組が合うだけでは、平面全体の正しさは確認できません。
4. **絶対値だけがずれるなら基準円を確認する。** 半径と直径の取り違え、中心・円周の
   指定、入力したゲーム内半径を確認します。
5. **位置・方向でずれが残るならカメラの前提を再検討する。** ゲーム側のカメラ変更、
   非等方な拡縮、高低差などを調べ、必要なら床の直交線や既知の円から再校正します。

余白だけを取り除くことと、ゲーム映像そのものを切り落とすことは異なります。
後者では、元の高さや投影の中心が分からなくなります。「床だけ」に切り抜いても
正しくなるわけではありません。映像に重ねられた帯も、外側に追加された余白とは別扱いです。

## 開発・検証で守ること

以下は領域設定や検出を変更するときに維持する前提と検証条件です。

- 最初に描画領域を確認する。検出失敗だけを理由に共通のピッチ角や
  画角を変更すると、既に合っている画像の補正も変わる。
- 自動判定の失敗を「画像全体が正しい」と断定しない。判定結果の表示・手動指定を
  含め、画像はブラウザ内で処理する。
- 領域やカメラを変更するときは、既存ピンの画像上の位置を維持する。
  現在ピンと自由な円中心は地面座標で保存されるため、投影だけ変えると画像上で動く。
  旧投影で画像座標へ戻し、新投影で地面座標へ変換する。
  基準円は中心と円周上の一点を保ち、測距・グループ中心・補助円・Undoを整合させる。
- 距離ラベルだけに倍率を掛けて症状を隠さない。ピン、円、画面表示、PNG出力が
  同じ投影とスケールを使う状態を保つ。

変更時には、少なくとも次の性質を確認します。

| 検証 | 期待する結果 |
| --- | --- |
| 同じ映像に対称・非対称の帯や外枠を追加し、正しい領域を指定 | 同じ対応点間の距離比が変わらない |
| 画像、領域、点を同じ倍率で拡縮 | 距離比が変わらない（丸め・入力誤差を除く） |
| 自動判定をホームインジケーターや操作部付き画像に適用 | 領域の指定による検証と分けて、判定失敗を検出できる |
| 手前・奥と異なる方向の既知の長さを比較 | 一つの基準への一致だけで判断しない |
| ズーム・スクロール・PNG出力 | 同じ点、円、数値が対応する |

モデルから作った画像を同じモデルで戻すテストは計算の整合性を確認できますが、
実際のゲームのカメラを正しく表している証明にはなりません。
実画像の検証では、点・領域・カメラ値・既知の長さの根拠・許容誤差を一緒に記録します。
