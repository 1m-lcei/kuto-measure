# ホバー判定の検証記録

ホバー判定の比較・測定条件・結果を記録します。現在の仕様は[開発文書](development.md#保存と表示)を参照してください。

## 契約と採用設計

比較元は `10d418a` の `App.svelte:updateHover`。`tests/hover-reference.ts` に独立した旧判定を残し、新実装と照合する。

- 重なった対象をすべて返す。最前面だけには限定しない。同じ対象の本体とラベルは同じキーにまとめる。
- `.hit`、`.line-hit`、`.label-hit` は選択用の透明領域なので対象外。
- 図形の塗り・線は従来どおり `isPointInFill` / `isPointInStroke`、文字は画面上の外接矩形で判定する。破線・端点・線の結合はブラウザの判定を維持する。
- ゲーム領域の外、Space操作中、パン中、ダイアログ表示中などの除外は `App.svelte` に残す。選択モードの判定、PNG、履歴は変更しない。

`src/hover.ts` は座標変換を1回だけ求め、各注釈の画面上の外接矩形で遠い対象を除外する。残った対象だけ従来の精密判定へ進める。矩形には線のはみ出しを含む保守的な余白を加え、余白に入っただけではヒット扱いにしない。

現在の描画契約は、子要素の個別変換がなく、表示線幅が最大4 CSS px（キーボードフォーカス時は4 SVG単位）、miter limitが既定の4であること。余白は8 × max(1, SVG倍率) px。この描画契約を変更するときは、この上限と差分回帰も見直す。SVGの線の定義は [SVG 2 Painting](https://svgwg.org/svg2-draft/painting.html#StrokeMiterlimitProperty) を参照。

アプリ独自のキャッシュや空間索引を持たず、毎回その時点のDOMを見る。編集、倍率、移動、リサイズ、フォント、画像切替に対する失効管理を追加しない。対象数に対する走査はO(N)のまま。

## 比較した代替案

| 案 | 判断 |
| --- | --- |
| 座標変換だけを共有 | 効果はあるが、全形状のスタイル・精密判定が残る。下表の実測でも候補除外を加えた方が軽い。 |
| モデル座標だけで幾何判定 | 投影データは再利用できるが、破線、塗り、線幅・結合、ブラウザの文字外接矩形まで別実装で一致させる必要がある。今回の規模では採らない。 |
| elementsFromPoint等の通常のヒットテスト | pointer-eventsを無効にした文字・線、透明な選択領域、すべての重なりを対象とする現行仕様とそのまま交換できない。描画・選択まで変えない。 |
| グリッド、木構造、矩形キャッシュ | 候補探索はさらに減らせるが、ズームに伴うラベル配置や描画更新の失効管理が増える。今回の単純な方式で十分な削減を得たため見送る。 |

## 測定方法

Windows x64、Ryzen 7 9700X、Chromium 153.0.8010.12、1440×1000、DPR 1。生成画像1536×709、外部データ・ネットワークなし。

- 通常量：24ピン、8距離線、3補助円、1基準円、1グループ。
- 多数：240ピン、80距離線、12補助円、1基準円、1グループ。
- 176点：固定seedの64点と、線・円・マーカー・文字の中心や境界付近。重なったピンも含む。
- 関数計測：同じ描画済みDOM上で旧判定、変換共有のみ、採用方式を直接呼ぶ。3周ウォームアップ後、実行順を巡回させた5試行。各試行3周の平均時間を1回あたりに換算。API呼出回数は時間計測と別に取得。
- アプリ計測：比較元と変更後のproduction buildそれぞれで、pointermove→rAF→ホバー判定→Svelte更新を実行。120移動×3試行。CDPのTaskDuration等の差分を移動数で割る。テスト側のイベント送出、ブラウザや描画更新の作業も含むため、ホバー関数単体の時間ではない。
- ブラウザテストと性能計測は同時実行しない。他プロセスの負荷やCPUクロックは固定していない。

全試行の生データは [performance/hover.json](performance/hover.json)。関数比較の表は同一プロセス内の `after`、アプリ比較は `before` と `after` を使う。

## 結果

中央値、括弧内は試行平均の最小〜最大。単位はms/回であり、個々の呼び出しのp95ではない。

| 関数計測 | 旧判定 | 変換共有のみ | 採用方式 |
| --- | --- | --- | --- |
| 通常量 | 0.410 (0.390–0.444) | 0.246 (0.236–0.274) | 0.074 (0.070–0.087) |
| 多数 | 4.685 (4.161–4.982) | 2.473 (2.418–2.745) | 0.707 (0.673–0.905) |

| 1回あたりのAPI呼出数（平均） | 通常・旧→新 | 多数・旧→新 |
| --- | --- | --- |
| querySelectorAll | 75 → 6.04 | 669 → 35.66 |
| getScreenCTM | 97.60 → 1 | 907.66 → 1 |
| getComputedStyle | 97.60 → 5.24 | 907.66 → 36.42 |
| isPointInFill + isPointInStroke | 98.59 → 5.26 | 908.65 → 36.44 |
| getBoundingClientRect | 36.82 → 75.69 | 333.41 → 695.78 |

矩形取得は増えるが、DOMの内側の走査・座標変換・スタイル取得・精密判定を減らせている。

| 実アプリのTaskDuration/移動 | 比較元 | 変更後 |
| --- | --- | --- |
| 通常量 | 1.608 (1.518–1.705) | 1.162 (1.157–1.220) |
| 多数 | 8.196 (7.903–8.615) | 4.155 (4.095–5.199) |

この条件のメインスレッド作業時間中央値は約28%・49%減。フレーム間隔p95の中央値は通常17.7→18.0 ms、多数18.9→18.0 msで、表示更新周期に近い。ホバー関数の短縮率を、そのままFPSや体感速度の向上率とは扱わない。ScriptDuration単独にも明確な改善傾向は出ていない。

性能の数値はChromiumのみ。Firefox・WebKitは判定の正しさを検証した。実機スマートフォン、数千注釈、ほぼ全対象の外接矩形が重なる配置の性能は未測定。大きな円・長い線の矩形が多数重なる場合は、候補除外の効果が小さくなりうる。

## 再現と回帰

```sh
bun run build
bun tests/hover-performance.ts
bun run test:browser
```

`PERF_DIST` に別途ビルドした比較元のディレクトリ、`PERF_LABEL` に出力名を指定できる。結果は `test-results/hover-<label>.json`。既存の `tests/performance.ts` と `test:performance` は変更していない。

`tests/hover.ts` を既存の3ブラウザ検証に組み込み、旧判定との差分と実際の薄表示を照合する。通常量・多数注釈、文字、細線・円の境界、重なり、キーボードフォーカス、最大10倍ズーム、パン、リサイズ、編集、Undo/Redo、画像切替、JSON復元、手動ゲーム領域のクリップを扱う。既存の円内部・重なりラベル等のテストも継続する。

型チェック（警告0）、lint、単体33件、ビルド、Chromium・Firefox・WebKitの全ブラウザ検証が成功。性能値に固定の合否閾値は設けていない。
